# Muslingo — исторический исходный аудит

> **Статус на 2026-08-11:** этот файл сохраняет исходные 36 находок и их
> первоначальные рекомендации. Он не является списком текущих открытых ошибок:
> большая часть пунктов ниже уже исправлена, а номера строк изменились.
> Актуальный подтверждённый статус, внешние блокеры и результаты последних
> тестов находятся в `PROJECT_STATUS.md`.

Сводит пять независимых ревью (безопасность, корректность, БД/инфра, готовность к сторам, производительность) в один приоритизированный список. Дубли объединены, находки сгруппированы тегом области `[Сторы]`, `[Безопасность]`, `[Корректность]`, `[БД]`, `[Перф]` и отсортированы по серьёзности Critical → Low. Всё проверено по коду (read-only), ключевые находки перепроверены вручную.

**Вывод о готовности.** Серверная безопасность закалена образцово — критичных/высоких дыр (инъекции, IDOR, обход аутентификации, SSRF) нет; всё, что осталось по безопасности — Medium и ниже. Однако к **сторам приложение сейчас не готово физически**: два Critical-блокера подписи (Android подписан debug-ключом, iOS без команды подписи) делают загрузку в Play/App Store невозможной, а High-блокер с прод-URL приведёт к «обрезанному» приложению без аккаунтов/синка/произношения. К **проду по данным** есть один High-риск: схема БД неаддитивна — на уже существующих в проде таблицах новые колонки не появляются, и часть роутов молча падает в 500. По качеству: «жирные» шрифты фактически отсутствуют (High, ломает всю типографику), плюс набор Medium-дефектов игровой логики (дневная цель, бонус за страйк, восстановление жизней) и перф-издержки.

**Минимальный набор для запуска:** закрыть 2 Critical + 3 High (подписи, прод-URL, миграции схемы, реальные Bold-шрифты) и добавить рабочий URL политики конфиденциальности (Medium-блокер листинга Play).

## CRITICAL

### C1. `[Сторы]` Android-релиз подписан debug-ключом
**Файл:** `android/app/build.gradle:35-39`
**Суть:** `release { signingConfig = signingConfigs.debug }`; нет `key.properties`, нет release-keystore (подтверждено — блок содержит `// TODO: Add your own signing config`).
**Сценарий вреда:** Google Play отклоняет AAB/APK, подписанный стандартным debug-ключом («You uploaded an APK signed in debug mode»). Сабмит физически невозможен.
**Рекомендация:** Создать release-keystore, добавить `signingConfigs.release` из `key.properties` (файл в `.gitignore`), переключить `release` на него. Ключ генерирует владелец (секрет).

### C2. `[Сторы]` iOS без команды подписи/провижининга
**Файл:** `ios/Runner.xcodeproj/project.pbxproj:454,577,634`
**Суть:** `CODE_SIGN_IDENTITY = "iPhone Developer"`, `DEVELOPMENT_TEAM` не задан.
**Сценарий вреда:** Без Apple Developer Team архивирование/загрузка в App Store Connect невозможны.
**Рекомендация:** В Xcode выбрать Team, сгенерировать сертификаты/профиль. Требует Apple Developer аккаунт ($99/год).

## HIGH

### H1. `[БД]` Схема неаддитивна — новые колонки не применяются к уже существующим таблицам
**Файл:** `server/lib/db.js:52-113` (`createSchema`)
**Суть:** Управление схемой держится только на `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`. Ни одного `ALTER TABLE` в проекте нет. `CREATE TABLE IF NOT EXISTS` — no-op на уже существующей таблице: не добавляет новые колонки и не навешивает новые `CHECK`.
**Сценарий вреда:** В проде таблицы созданы более ранней версией схемы. Любая колонка, добавленная позже (`muslingo_push_subscriptions.last_sent_date/due_count/learning_goal/installation_id`, `muslingo_progress.weekly_xp/week_start`, `muslingo_users.guest_imported`), на такой БД не появится. Каждый INSERT/SELECT/UPDATE к недостающей колонке (`push-subscribe`, `cron-reminders`, `progress-complete`, `progress-sync`) падает `column ... does not exist` → HTTP 500. Односторонняя дверь: миграция «прошла» без ошибки, но роут молча ломается.
**Рекомендация:** Ввести аддитивный слой миграций — `ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...` для каждой добавленной колонки/констрейнта внутри `createSchema`, либо версионированный runner (таблица `schema_migrations`).

### H2. `[Сторы]` Прод-URL бэкенда не зашит в релиз, по умолчанию localhost
**Файл:** `lib/services/backend_service.dart:64-75` (использование `hasConfiguredApiUrl` в `app_state.dart:454,469`)
**Суть:** Без `--dart-define=MUSLINGO_API_URL=…` `apiBaseUrl` = `http://10.0.2.2:8090` (Android) / `http://127.0.0.1:8090` (iOS), а `hasConfiguredApiUrl=false` отключает регистрацию/вход/синк (подтверждено).
**Сценарий вреда:** Обычная `flutter build appbundle --release` даёт приложение без облачных аккаунтов, друзей, лидерборда, синхронизации, проверки произношения (`speech_evaluation_service.dart:73`) и аудио Корана (`lesson_screen.dart:431`). Ревьюер видит «обрезанное» приложение → риск отказа + функции не работают.
**Рекомендация:** Собирать с `--dart-define=MUSLINGO_API_URL=https://<прод-домен>` (бэкенд на Vercel уже есть); зафиксировать в скрипте сборки/CI.

### H3. `[Перф]` Шрифты Nunito Bold/ExtraBold — побайтовые копии Regular
**Файл:** `pubspec.yaml:66-74` + `assets/fonts/`
**Суть:** `md5` совпадает (перепроверено: все три = `1f0e8654e8e57040425c8ce20b01af9f`). «Жирные» начертания физически отсутствуют — это Regular под другими именами.
**Сценарий вреда:** 177 мест с `FontWeight.w700/w800/w900/bold` для Nunito (заголовки, кнопки, статистика) рендерятся обычным весом → вся типографика «плоская», дизайн-иерархия теряется. Плюс ~540 КБ впустую в бандле.
**Рекомендация:** Положить настоящие Bold/ExtraBold `.ttf`; если жирных нет — убрать лишние `weight`-объявления, не использовать `w800/w900`. Проверить визуально после замены.

## MEDIUM

### M1. `[Безопасность]` Накрутка недельного лидерборда: нет лимита/дневного потолка на `progress/complete`
**Файл:** `server/routes/progress-complete.js:32-43, 94-106`
**Суть:** Единственная защита от повтора — точное совпадение `rewardToken` (`isRewardReplay`). Но токен полностью клиентский (по умолчанию `${lessonId}:${Date.now()}`, перепроверено на `:41`), поэтому клиент генерирует уникальный токен на каждый запрос. За каждый повтор — `+5` XP и `weekly_xp + 5` без дневного потолка и без rate-limit.
**Сценарий вреда:** Авторизованный пользователь скриптом шлёт N раз `POST /api/progress/complete` с валидным `lessonId` и разными `rewardToken` → `weekly_xp` растёт линейно → первое место в топ-50 недели. Оптимистическая блокировка по `version` не мешает (последовательные запросы просто инкрементят версию).
**Рекомендация:** Серверный дневной потолок XP/завершений на пользователя (счётчик per-day в документе) и/или rate-limit на роут по user_id, как для логина.

### M2. `[Корректность]` `dailyProgress` не сбрасывается в начале нового дня (клиент И сервер)
**Файлы:** `lib/services/app_state.dart:955-956` (+ геттер `todayProgress` `:108-114`); `server/routes/progress-complete.js:86`
**Суть:** Прогресс дневной цели считается как `(_user.dailyProgress + 1).clamp(0, dailyGoal)` (клиент) и `Math.min(dailyGoal, dailyProgress + 1)` (сервер, перепроверено `:86`). Ни один путь не обнуляет `dailyProgress` при смене дня; геттер `todayProgress` прячет вчерашнее значение только ДО первого урока нового дня.
**Сценарий вреда:** Вчера 3 урока (`dailyProgress=3`, цель 3). Сегодня 1 урок → `min(3+1,3)=3` → кольцо цели (`home_screen.dart:207-210`) сразу «3 из 3». Фича дневной цели сломана для любого вернувшегося пользователя (и локально, и на backend).
**Рекомендация:** При смене дня (`newDay`/`diff>=1`) ставить `dailyProgress = 1`, а не инкрементить старое — симметрично клиент и `progress-complete.js`. Покрыть тестом (сейчас проверяется только первый урок первого дня).

### M3. `[Корректность]` Дублирование бонуса за страйк при нескольких уроках в день-milestone (локальный/гостевой путь)
**Файл:** `lib/services/app_state.dart:918-925` (использование `:929`, `:994`; ветка «тот же день» `:907-909`)
**Суть:** `streakBonus` начисляется по `if (newStreak == 7) …` каждый раз. В ветке `diff == 0` (второй урок в тот же день) `newStreak` не меняется (7/30/100), поэтому бонус начисляется повторно на каждом уроке дня. На сервере этого нет — там бонус ограничен `newDay && streak === …` (`progress-complete.js:71`, перепроверено).
**Сценарий вреда:** В день со страйком 7 гость проходит 3 урока → `+10 XP` бонуса трижды (в `newXp` и в лиговом XP), экран итога показывает «Бонус за страйк» каждый раз. Инфляция XP на клиентском/гостевом пути.
**Рекомендация:** Начислять `streakBonus` только когда день реально сменился (ветка `diff == 1`), как на сервере.

### M4. `[Корректность]` Восстановление жизней по времени работает только при холодном старте — возможен «мягкий лок»
**Файлы:** `lib/services/app_state.dart:256` (`refreshHearts`) и `:191` (`nextHeartAt`) — не вызываются; `_applyHeartRegen` только в `_loadUser` (`:394`) и `loginAsGuest` (`:432`); нет `WidgetsBindingObserver` в `main.dart`/`main_tab_screen.dart`. Блокировка старта урока — `home_screen.dart:258`.
**Суть:** Регенерация жизней применяется только при пересоздании `AppState` (запуск/перезагрузка). Пока приложение открыто, жизни не восстанавливаются; обратного отсчёта нигде нет.
**Сценарий вреда:** Не-премиум с `hearts==0` и `<20` энергии: `_openLesson` не даёт начать урок → энергию не заработать → жизни не регенерируются в сессии → пользователь заблокирован, пока не перезапустит приложение. Ломает заявленную в FAQ механику.
**Рекомендация:** Подключить `WidgetsBindingObserver` (resume) и/или таймер, вызывающий `refreshHearts()`; показать `nextHeartAt` как обратный отсчёт в `_HeartRestoreSheet`.

### M5. `[БД]` Нет индекса на FK-колонку `muslingo_friendships.friend_id`
**Файл:** `server/lib/db.js:106-112`
**Суть:** PK `(user_id, friend_id)` даёт индекс по префиксу `user_id`, но не по одиночному `friend_id`, который объявлен `REFERENCES ... ON DELETE CASCADE`.
**Сценарий вреда:** При удалении аккаунта (`account.js`) каскад по `friend_id` требует `WHERE friend_id = <deleted>` → seq scan всей таблицы дружб при удалении любого пользователя, под блокировкой. Деградирует линейно с ростом таблицы.
**Рекомендация:** `CREATE INDEX IF NOT EXISTS muslingo_friendships_friend ON muslingo_friendships (friend_id)`.

### M6. `[БД]` Нет индекса на FK-колонку `muslingo_push_subscriptions.user_id`
**Файл:** `server/lib/db.js:79-95` (колонка `user_id` — `:85`)
**Суть:** `user_id uuid REFERENCES muslingo_users(id) ON DELETE SET NULL`, индекса нет.
**Сценарий вреда:** (а) `account.js:14` `DELETE ... WHERE user_id = ...` — seq scan; (б) каскад `SET NULL` при удалении юзера тоже сканирует всю таблицу. С ростом подписок каждое удаление аккаунта сканирует таблицу целиком.
**Рекомендация:** `CREATE INDEX IF NOT EXISTS muslingo_push_user ON muslingo_push_subscriptions (user_id)`.

### M7. `[БД]` Потолок рассылки `LIMIT 2000` — «хвост» пользователей молча перестаёт получать напоминания
**Файл:** `server/routes/cron-reminders.js:117-125`
**Суть:** Кандидаты — `WHERE enabled = true AND updated_at > now() - interval '120 days' ORDER BY updated_at DESC LIMIT 2000`. Лимит применяется по `updated_at` ко всем включённым подпискам ДО фильтрации по окну напоминания.
**Сценарий вреда:** Как только активных подписок > 2000, пользователи с более старым `updated_at` не попадают в топ-2000 и никогда не оцениваются на своё окно. Напоминания тихо отваливаются для части базы; по метрикам не видно (200 OK, `checked` упирается в 2000).
**Рекомендация:** Выбирать по бакету времени (условие/индекс на `(enabled, reminder_hour, reminder_minute)` и `last_sent_date IS DISTINCT FROM today`), убрав зависимость от `updated_at`-ранга; либо пагинация по курсору.

### M8. `[БД]` Push-подписки только выключаются, но никогда не удаляются — рост таблицы и бессрочное хранение ПДн
**Файл:** `server/routes/cron-reminders.js:98-100` (404/410 → `enabled=false`); таблица `db.js:79-95`
**Суть:** Мёртвые endpoint'ы переводятся в `enabled=false`, но строки остаются навсегда с ПДн: `endpoint`, ключи `p256dh`/`auth_secret`, `timezone`, `learning_goal`, `installation_id`. При удалении аккаунта у анонимных/чужих подписок `user_id` не трогается.
**Сценарий вреда:** Таблица растёт «кладбищем» отключённых подписок; крипто-ключи устройства и адрес доставки push хранятся бессрочно без привязки к живому аккаунту (рост + вопрос retention/приватности).
**Рекомендация:** Периодически `DELETE WHERE enabled = false AND updated_at < now() - interval '30 days'` (на том же cron-проходе) или жёсткий `DELETE` при 410 Gone.

### M9. `[Сторы]` Нет ссылки на политику конфиденциальности внутри приложения
**Файл:** `lib/screens/settings_screen.dart` (только e-mail `support@muslingo.app`; ссылок на privacy/terms во всём `lib/` нет)
**Суть:** `PRIVACY_POLICY.md` лежит в репо, но нигде не хостится и не открывается из приложения.
**Сценарий вреда:** У приложения есть регистрация → Apple 5.1.1(i)/(v) и Google Play требуют доступную политику. Play-листинг вообще не сабмитится без Privacy Policy URL; отсутствие рабочего URL — частая причина отклонения.
**Рекомендация:** Опубликовать политику по стабильному URL (`/privacy`), добавить кнопку-ссылку в настройки/онбординг. URL требует вашего домена.

### M10. `[Сторы]` Нет app-level Privacy Manifest (`PrivacyInfo.xcprivacy`)
**Файл:** отсутствует в `ios/Runner/`, не подключён в `project.pbxproj`
**Нюанс:** required-reason API покрыты манифестами плагинов (`shared_preferences_foundation`, `path_provider_foundation`, `sqflite_darwin`, `connectivity_plus`, `flutter_local_notifications`, `google_sign_in_ios`, `package_info_plus`, `url_launcher_ios`), поэтому авто-отклонения по «reason API» не будет.
**Сценарий вреда:** Без app-level манифеста (`NSPrivacyTracking=false` + типы данных) выше риск ручных вопросов ревью и рассинхрон с App Privacy-лейблами.
**Рекомендация:** Добавить `ios/Runner/PrivacyInfo.xcprivacy` (tracking=false; данные: email/имя/прогресс), включить в таргет Runner.

### M11. `[Перф]` IndexedStack держит все 5 вкладок живыми, каждая на `context.watch`
**Файл:** `lib/screens/main_tab_screen.dart:35-39` (+ `body: IndexedStack(...)`)
**Суть:** Все 5 экранов (`HomeScreen` ~1357 строк, `QuranScreen`, `CoachScreen`, `RulesScreen`, `ProfileScreen`) строятся сразу и остаются в дереве; каждый в `build` делает `context.watch<AppState>()`.
**Сценарий вреда:** Любой из 33 `notifyListeners()` в `AppState` (тик регенерации жизней, синк) перестраивает все пять вкладок, включая невидимые. Плюс `CatCharacter` в скрытых вкладках (`quran_screen.dart:177`, `coach_screen.dart:304`, `profile_screen.dart:191`) — `AnimationController..repeat()` крутится каждый кадр (IndexedStack не глушит тикеры скрытых детей) → лишний CPU/батарея в простое.
**Рекомендация:** Сузить подписку (`Consumer`/`Selector` вокруг зависящих виджетов вместо `watch` на весь экран); скрытые вкладки в `TickerMode(enabled: isCurrent)` / ленивая сборка.

### M12. `[Перф]` Крупные PNG-коты декодируются в полном разрешении
**Файл:** `lib/widgets/cat_character.dart:61`, `lib/main.dart:301-306`
**Суть:** `Image.asset`/`AssetImage` без `cacheWidth`/`cacheHeight`/`ResizeImage`. Исходники большие: `muslingo_cat.png` 781 КБ (показ 190×190), `cat_*_real.png` 223–647 КБ (показ 38–230 px), всего ~3.3 МБ PNG, 15 экземпляров.
**Сценарий вреда:** `ImageCache` хранит растр в полном пиксельном размере независимо от размера на экране → большой расход памяти на декодированные битмапы (особенно на web), GC-паузы на слабых устройствах.
**Рекомендация:** Задать `cacheWidth`/`cacheHeight` под фактический размер (с `devicePixelRatio`); дополнительно ужать сами PNG.

### M13. `[Перф]` Осиротевший экран лидерборда + серверная цепочка (мёртвый код)
**Файл:** `lib/screens/leaderboard_screen.dart` (435 строк)
**Суть:** `LeaderboardScreen` нигде не импортируется (перепроверено grep — только само-ссылки внутри файла): нет в маршрутах `main.dart` и в табах; комментарий `main_tab_screen.dart:30-33` прямо говорит, что вкладку убрали. Ради него живут `AppState.fetchLeaderboard` (`app_state.dart:1081`), `BackendService.getLeaderboard` (`backend_service.dart:182`), `_localLeaderboard`.
**Сценарий вреда:** ~600 строк недостижимого кода + модель `LeaderboardEntry`; ложное впечатление рабочей фичи, неиспользуемый сетевой путь, усложнение поддержки.
**Рекомендация:** Удалить экран и связанные методы, либо вернуть точку входа (напр., из «Друзей», как обещает комментарий).

## LOW

### L1. `[Безопасность]` Перечисление аккаунтов при регистрации + отсутствие rate-limit
**Файл:** `server/routes/auth-register.js:22-39` (маппинг `23505 → 409 already_exists` в `server/lib/http.js:128-129`)
**Суть:** Дубликат email → `409 already_exists`, подтверждает существование аккаунта (осознанный компромисс, клиент подсказывает «войдите»). Логин от перечисления защищён образцово. На `register` нет rate-limit — возможна массовая регистрация (каждая гонит scrypt).
**Рекомендация:** Полное закрытие перечисления требует email-verification; добавить per-ip rate-limit на `register`.

## Что уже сделано хорошо (проверено, замечаний нет)

**Безопасность.** SQL-инъекций нет (tagged-templates neon; вычисляемые `idBounds` в `friends.js` — связанные параметры, валидация hex). JWT: `algorithms: ['HS256']` пинится, проверяются `iss/aud/exp/nbf`, `sub` как UUID, секрет ≥32 симв. Логин: единый тайминг/ответ (dummy-scrypt для несуществующего email), два rate-limit (pair+ip), IP как правый элемент XFF. SSRF на push закрыт allowlist'ом хостов. IDOR нет — всё скоуп-нуто по `user.id`; лидерборд не отдаёт UUID; friends не отдаёт email/UUID. Отписка push требует доказательства владения; cron авторизуется через GitHub OIDC (JWKS) или `CRON_SECRET`, fail-closed. Reward-replay guard и потолки гостевого импорта продуманы. Локальные пароли — PBKDF2-HMAC-SHA256 (12000 итер., соль, constant-time, авто-миграция плейнтекста). Заголовки HSTS/`X-Frame-Options: DENY`/`nosniff`/CSP/`no-store`, обезличенные ошибки, секретов в коде нет, CORS по `MUSLINGO_APP_ORIGIN`, cookie не используются → нет CSRF-вектора.

Каскады ориентированы верно (кроме отсутствующих FK-индексов M5/M6). Индексы под горячие запросы присутствуют (лидерборд, cron-выборка, поиск друга по коду, логин по email).
